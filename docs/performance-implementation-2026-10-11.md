# BALD 0.1.7 개선 실행 결과

감사 기준: `performance-code-audit-2026-10-10.md`. 변경 전 비교 대상은
`git archive HEAD`로 보존한 **0.1.7 소스**다. 설치된 0.1.6의 수치를 사용하지 않았다.
원본 커밋: `1a991a4577b3009e0e9b7d21146166d8022fbfbe`.

## 릴리스 후보 최종 정리 확정

사용자의 최종 정리 지시에 따라 추가 개발·벤치마크·실제 환경 테스트를 종료한다.
아래 항목별 처리표와 현재 소스의 구현 경로를 대조했으며 **26개 적용**을 유지한다:
B01–B14, O01–O03·O05–O10, Q01–Q03. 적용은 실제 게임·관리자·설치 검증 완료를 뜻하지 않는다.
**O04·O11·O12는 0.1.7에서 보류 확정**이다. 기존 4초 reconciliation, 폰트와 CSS를 유지한다.

최종 정리 단계에서는 실행 코드·테스트·버전·의존성을 변경하지 않았으며 기존 변경과
Rust 104개 + 별도 worker 2개, JS 29개 통과 기록 및 fmt/Clippy/check/build/lint 결과를 보존했다.
테스트나 성능 측정을 다시 실행하지 않았다. Chromium 1412는 기존 코드와 수정 코드의
종료에서 모두 관찰됐으며 명확한 결함이 확인되지 않아 추측으로 수정하지 않았다.

실제 게임 호환성, UAC/관리자 접근, 실제 포커스·트레이 메뉴, 자동 시작·예약 작업,
설치·업데이트·제거 및 원격 CI는 미검증으로 남긴다. 현재 후보는 사용자 검증용 로컬
release EXE이며 설치된 BALD를 변경하거나 실행하지 않았다. 사용자 설정·시작 메뉴·
레지스트리·예약 작업 변경, commit/push, 버전 변경, 릴리스는 수행하지 않았다.
소스와 보존 로그의 SHA-256 목록 및 후보 EXE 확인은
`artifacts/release-candidate-2026-10-11/final-state.json`에 기록한다.

## 자리비움 승인 이후 실제 환경 검증

사용자가 자리를 비운 동안 미검증 부분 진행을 요청한 뒤 Windows 검증을 재개했다.
현재 세션은 관리자 권한이 아니며 UAC 승인을 받을 수 없으므로 승격을 요청하지 않는다.
설치/업데이트/삭제, 사용자 설정/자동 시작/예약 작업/바로가기 변경, commit/push는 하지 않는다.
실제 메이플스토리 프로세스가 없어서 게임 호환성은 계속 미검증이다.

- 최종 Win32 fixture 전체: **104 통과, 0 실패, 기존 worker 진입점 2개 ignored**,
  112.39초. `artifacts/native-tests/suite-20261011-084108-1.log`.
  새 캡션 회귀 추가 전 전체 실행도 103/0/2, 110.11초로 통과했다.
- 별도 worker 부모/자식: 각각 **1 통과, 실패 0**. 일반 권한의 실제 프로세스/TCP로
  UI 상태 유지, OFF/연결 종료 복원, 연결 실패/종료 확인 뒤 로컬 재개를 검사했다.
  `artifacts/native-tests/worker-20261011-083852-1.log`.
  관리자 게임 접근과 실제 권한 상승을 검증한 것은 아니다.
- B01의 실제 Win32 콜백 회귀를 추가했다. 중간 `WM_WINDOWPOSCHANGED`에서 소유자가
  `WS_DISABLED`를 설정한다. 이전 전체 스타일 쓰기를 일시 복원하니 같은 테스트가 실패했고,
  수정 복구 뒤 **3회 통과**했다. 의도한 실패 로그는 `caption-20261011-084035-1.log`,
  통과는 `caption-20261011-084044-{1,2,3}.log`다. 미해결 테스트 실패가 아니다.

  최종 일반 EXE는 다시 빌드했으며 설치된 앱 대신 독립 식별자의 검증 복사본을 실행한다.
- 측정 종료 후 fmt, Clippy `--all-targets --locked --offline -- -D warnings`, release check,
  `npm run lint`, JS 테스트를 다시 실행해 모두 종료 코드 0, JS **29/0**을 확인했다.
  검사 도구 5개 PowerShell 구문 오류 0, `git diff --check` 오류 0이다.

### 실제 WebView2와 종료 경고

최종 생산 코드의 WebView 수명 경로를 복사한 `Bald Probe validation`을 일반 데스크톱과
격리 데스크톱에서 각각 실행했다. 테스트 복사본은 앱/인스턴스/활성화 식별자를 분리하고
가짜 설정 파일만 사용한다. 자동 적용·자동 시작·업데이트를 차단하며 UAC launcher를
오류 반환으로 대체한다. 실행 중인 게임 창을 등록하거나 수정하지 않는다.
복사본에서 제외한 기능 때문에 발생한 13개 unused/dead-code 빌드 경고는 숨기지 않았다.
이는 생산 소스의 Clippy 진단이 아니며 생산 검사는 경고 0이다.

각 실행에서 **6회 닫기/재열기**, **6회 언어/테마 ACK**, 네이티브 닫기와 프런트엔드
닫기, 최소화 뒤 닫기, 닫는 중 재열기, 두 번째 실행에 의한 열기, 위치/크기 유지,
백그라운드 감시 지속 및 비동기 오류 0을 확인했다. 일반 실행 종료 뒤 같은 검증용
프로필 식별자의 WebView2 프로세스는 **0개**였다.
근거는 `validation/bald-probe-validation-ui-{current,isolated}.events.jsonl`과 native 로그다.

일반 데스크톱의 `Error removing system tray icon`은 **0회**, 격리 데스크톱은 **1회**였다.
따라서 Explorer 없는 격리 환경과 연관된 결과를 얻었지만 모든 사용자 트레이 오류가
같은 원인이라고 단정하지 않는다. Chromium 1412는 **두 환경 모두 종료 시 관찰**됐다.
격리 데스크톱만의 경고라는 설명은 철회한다. 종료 코드 0과 프로세스 잔류 0을 확인했지만
무해함이나 모든 비동기 정리 완료를 일반화하지 않으며 의존성 구조를 추측으로 바꾸지 않는다.

일반 실행의 생성 시작 → 상태/폰트/진입 모션 완료 신호까지는 최초 **1,248.7ms**,
재생성 6회 **829.6~1,081.3ms**, 중앙값 **1,071.5ms**였다.
이는 `interactive-ready` 계측 신호까지의 시간이며 네이티브 창 생성 시간과 다르다.
표시 픽셀/입력 지연을 사람이 확인한 값이나 완전한 cold-boot 측정은 아니다.
`validation/ui-ready-current.json`에 각 값을 보관했다.

트레이 helper의 **자기 PID/HWND에만** 네이티브 알림을 보내 3회 검사했다. 단일 왼쪽
클릭 알림은 창을 열지 않고 더블 클릭 알림은 기존 Tauri 트레이 콜백을 거쳐 창을 생성한다.
매회 닫기 뒤 main 창이 없어지는 것을 확인했다. `bald-probe-validation-tray.events.jsonl`의
3개 cycle과 passed 결과, 종료 코드 0, stderr 빈 파일이 근거다. 마우스 입력을 주입하지
않았으므로 실제 포인터 클릭, 트레이 메뉴 조작 및 포커스 전환까지 검증한 것은 아니다.
이 실행은 모든 WebView를 닫은 뒤 종료해 1412가 없었지만 이것만으로 경고 원인을 확정하지 않는다.

### 자리비움 중 같은 0.1.7 소스의 전후 비교

변경 전 `before/bald-probe-away{0,50}`와 최종 변경 후
`validation/bald-probe-validation{0,50}`을 같은 PC에서 순차 실행했다. 실행 중 다른
빌드/테스트 작업을 겹치지 않았다. 자동 적용하지 않는 가짜 규칙 0/50개이며 실제 게임 부하는
아니다. 각 구간 처음 5초를 제외하고 500ms 대기 간격의 표본을 사용한다. CIM 조회 시간이
추가되므로 정확한 2Hz 표본은 아니다. 전체 8개 구간 원자료/요약은
`artifacts/performance-2026-10-10/validation/comparison-away.json`에 보관했다.
해시·실행 시각·완료 표본은 `validation-provenance.json`에 기록했다. 마지막 50규칙
실행은 세션 반환이 보관되지 않아 종료 코드를 회수하지 못했다. 140.582초 최종 표본,
모든 구간 완료, 보고된 오류 0 및 프로세스 잔류 0은 확인했으며 종료 코드 0으로 기록하지 않았다.

아래 RAM은 본체와 WebView2 작업 집합의 합(MiB)이며 공유 페이지를 중복 셀 수 있다.
Private는 각 프로세스 private commit 중앙값의 합이며 실제 물리 RAM과 다르다.
CPU는 본체와 WebView2 CPU 시간 차이를 합한 **1코어=100%** 기준이다.
논리 프로세서 12개인 이 PC의 전체 CPU 비율로 환산할 때는 12로 나눈다.

| --- | ---: | ---: | ---: | ---: |
| 0 / 배경 | 397.06 → 23.23 | 263.93 → 3.20 | 0.163 → 0.000 | 6 → 0 |
| 0 / 표시 | 403.86 → 402.62 | 257.24 → 268.56 | 0.000 → 1.637 | 6 → 6 |
| 0 / 닫기 | 412.97 → 43.97 | 266.83 → 9.66 | 1.290 → 0.000 | 6 → 0 |
| 50 / 배경 | 481.91 → 23.82 | 350.07 → 3.33 | 4.483 → 0.000 | 6 → 0 |
| 50 / 표시 | 493.70 → 457.99 | 350.56 → 319.53 | 2.981 → 0.441 | 6 → 6 |
| 50 / 닫기 | 501.13 → 44.26 | 335.03 → 9.96 | 3.536 → 0.167 | 6 → 0 |

0.000은 짧은 구간에서 계측한 CPU 시간 증가가 없었다는 뜻이며 항상 CPU 0이라는
뜻이 아니다. CPU와 표시 중 RAM은 모든 구간에서 개선되지 않았다. 외부 WinEvent 입력을
고정하지 않은 단회 비교이므로 CPU 회귀/개선의 인과 관계를 확정하지 않는다.
최소화/단순 숨김은 WebView를 유지하되 상태 폴링을 멈추며, 실제 닫기는 해제한다.
규칙 50개의 최소화/숨김 작업 집합은 각각 504.43 → 427.99, 500.65 → 428.07MiB였다.

배경의 본체만 작업 집합은 0규칙 41.69 → 23.23, 50규칙 42.60 → 23.82MiB다.
50규칙 배경에서 전체 스레드/핸들 중앙값 합은 211 → 23 / 3,508 → 219,
닫기 후 201 → 26 / 3,620 → 428이었다. 반복 닫기 후에도 WebView2는 0개였고
작업 집합 44.68MiB, Private 10.73MiB로 배경 최초값에 완전히 돌아오지는 않았다.
본체 캐시/런타임까지 모두 반환됐다고 주장하지 않는다.

50규칙 표시 중 반복 상태 응답은 **5,574,379 → 2,717 bytes**,
상태 전송량은 2,823,287 → 1,313 bytes/s, 응답 중앙값은 50.6 → 1.7ms였다.
이는 초기 설정/아이콘 응답을 제외한 반복 status 비용이다. 이전 최소화/숨김의
약 0.486요청/s는 최종 코드에서 0으로, 닫기 및 배경도 0으로 확인했다.
초기 데이터 전송 비용을 제거했다는 뜻은 아니다.

picker 호출은 0규칙 60.9 → 54.6ms, 50규칙 48.3 → 49.2ms이며 모두 4개 창을 반환했다.
한 번씩 호출한 값이어서 O09의 보편적인 속도 향상 증거로 사용하지 않는다.
최종 네이티브 최초 생성 311.3/314.5ms, 해제 후 재생성 299.2/289.2ms는
기존 이미 생성된 창 표시 2.4ms 수준보다 길다. RAM 감소에 따른 재생성 비용이며
앞의 최초 UI 준비 1,248.7ms와 구분한다. 변경 전 전체 UI 준비 시간은 계측하지 않았다.

0규칙 watcher는 EnumWindows 이전에 반환했고 picker의 열거 1회만 기록됐다.
50규칙에서는 기록된 전체 열거당 경로 조회가 전후 모두 **4회**로 규칙 수만큼
증폭되지 않았다. 닫기 전환을 포함한 구간의 scan/EnumWindows는 0.333 → 2.224회/s였다.
최종 코드는 WebView 해제로 추가 창 종료 이벤트를 만들며 입력이 같지 않다.
동일 요청 10,000개 → 큐 1개인 순수 테스트와 기존 4초 reconciliation을 유지하고
이 수치만으로 O04 변경을 추가하지 않는다. 계수는 삽입한 함수 경로의 호출 수이며
모든 Win32 API, token 조회 또는 실제 allocator 비용을 포괄하지 않는다.

변경 전 두 비교 실행에서도 종료 시 Chromium 1412를 관찰했다. 최종 비교 실행의
stderr는 비어 있었고 검증 프로필의 WebView2 및 테스트용 앱 잔류는 0개였다.
UI lifecycle 실행에서는 여전히 경고가 발생했으므로 **종료 경고 원인은 미확정**이다.
UAC/관리자 게임 접근, 실제 메이플 드래그·해상도 변경, 실제 사용자 설치본의 포커스/트레이
메뉴, 자동 시작/예약 작업/설치/업데이트/제거는 실행하지 않았다.

## 최종 안정화: 실제 PC 테스트 금지 적용 이후

이 절은 금지 적용 당시의 작업 기록이다. 이후 자리비움 승인으로 재개한 최신 검증 및
미검증 범위는 위의 절을 우선한다.

아래의 기존 네이티브 테스트·UI 실행·RAM/CPU 측정은 **금지 지시 이전의 기록**이다.
사용자가 같은 PC를 사용한 외부 이벤트 차이를 통제하지 못했으므로 CPU 및 스캔 빈도의
증감만으로 코드 회귀를 확정하지 않는다. 이번 최종 안정화에서는 실제 창, 격리 데스크톱,
WebView2, 트레이, DWM, Shell, UAC, 서비스, 설치 및 실시간 벤치마크를 실행하지 않았다.
이전 결과를 최종 수정본의 실제 Windows/게임 검증으로 대신하지 않는다.

### 코드 대조 및 추가 수정

26개 적용 항목의 구현 경로와 기존 회귀 테스트를 대조했다. 새로운 의존성, 폰트/CSS 변경,
새 상태 머신이나 제품 기능 변경은 추가하지 않았다. 발견한 구체적인 누락은 B01의
`refresh_cached_caption`이다. 중간 프레임 갱신 뒤 이전 전체 스타일을 다시 쓰던 경로를
최신 스타일 조회 후 캡션 비트만 병합하는 방식으로 수정했다. 순수 병합 테스트는 모사한
소유자 콜백의 `WS_DISABLED`·가시성 변경 보존과 기존 쓰기 방식의 불일치를 확인한다.

100ms 이동 timeout은 OS 요청 취소의 증거가 아니므로 소유권을 보관한다. 게임이 이동을
계속 거부하는 경우나 매우 늦은 완료 뒤 최종 해제 위치 적용은 실제 환경 검증이 필요하다.
이 예외 경로를 추측으로 바꾸거나 강제 재시작 fallback을 추가하지 않았다.

### 동일 입력의 비용 및 수명 판단

- **규칙 0개:** `scan`은 `enumerate_windows` 이전에 반환한다. 따라서 watcher의
  전체 창 열거/프로세스 경로 조회는 0회다. 기존 기록의 scan 횟수는 이 조기 반환도 센다.
  picker는 별도의 창 열거를 할 수 있어 프로세스 전체 EnumWindows 0회라는 뜻은 아니다.
- **이벤트 병합:** 실제 생산 경로의 큐 함수에 동일 요청 10,000개를 넣으면 pending 중
  채널 메시지/네이티브 wake 필요 횟수는 1회, 소비 후 다시 1회다. 연결 종료 시 pending을
  해제하고 새 큐 요청을 받는다. 기존 원본의 pending/send 분기와 정책은 같으며 native
  메시지 전송은 호출하지 않았다. 규칙이 있으면 scan 1회당 EnumWindows 호출 경로는 1곳이다.
  실제 scan 실행/EnumWindows 계수 테스트가 아니라 큐 계수와 코드 경로 검토의 결론이다.
- **50규칙 × 100창:** 같은 입력에서 기존 3회 매칭은 경로 정규화 **30,000회**,
  공유 매칭은 **150회**다. 규칙별 결과와 창 포인터 순서가 같다. 비교 조건 판단은
  15,000쌍 → 5,000쌍이고 정규화의 대체 문자열 할당 호출도 30,000 → 150회다.
  실제 allocator 호출 수/바이트는 계측하지 않았다. 전체 매칭 복잡도는 여전히 O(R×W)다.
- **PID 조회:** 스캔 안에서 핸들 획득에 성공한 동일 PID는 경로 결과를 재사용한다.
  OpenProcess 실패는 캐시할 핸들이 없어 재시도 가능하다. 스캔 간 캐시는 만들지 않으며,
  규칙 수 증가만으로 한 스캔의 경로 조회가 증가하는 구조는 아니다. 기존 숨김 구간의
  스캔 4.398 → 10.647회/초 및 조회 39.581 → 89.771회/초는 다른 이벤트 입력의 기록이다.
- **숨김/최소화:** JS mock에서 타이머 0개, 표시 재개 즉시 1요청, 느린 요청도 중첩 0개를
  확인한다. destroy 이후 페이지의 타이머는 남길 보관 경로가 없다. picker/설정의 진행 중인
  blocking 작업은 닫기만으로 취소되지 않고 완료까지 실행할 수 있다. 이는 무한 폴링이 아니다.
- **WebView 없는 배경:** 감시의 4초 reconciliation과 서비스 복구 스레드의 4초 대기는
  의도적으로 유지한다. 업데이트 확인 작업도 UI와 독립적으로 완료될 수 있다. 페이지를
  유지하기 위한 반복 IPC나 WebView 재생성 루프는 없지만 모든 백그라운드 작업이 0개인 것은 아니다.

O04는 현재 병합·필터와 4초 reconciliation을 유지한다. 동일 이벤트 입력에서 새 전체
열거 증가가 확인되지 않았고 HWND 단독 처리는 생성/숨김/해상도/복원 재검증을 바꾼다.
O11은 라이선스·변환 후 렌더링/호환성 비교를 끝내지 못해 보류한다. O12는 실제 GPU 병목과
시각적 동일성 증거가 없어 보류한다. 셋 모두 완료 수에 포함하지 않는다.

## 기존 검증 방법과 범위: 금지 지시 이전 기록

`tools/windows/test-isolated.ps1 -Mode suite`는 `cargo test --no-run`으로 만든
실제 테스트 EXE를 다른 데스크톱에서 `--test-threads=1`로 실행한다.
현재 표시되는 데스크톱으로 전환하지 않으며 실제 키·마우스를 주입하지 않는다.
기존 ignored 두 항목은 별도 worker 부모/자식 진입점으로 모두 실행한다.
DWM과 시스템 자원은 데스크톱 간에 완전히 독립적이지 않다.

당시 검사 결과, 이번 최종 수정본 전체 재검사 결과는 아님:

  마지막 실행 110.50초, `artifacts/native-tests/suite-20261011-074100-1.log`.
- 별도 worker: 부모 1개와 자식 1개 모두 통과, 실패 0.
  `artifacts/native-tests/worker-20261011-074251-1.log`.

Rust 1.95.0, Node 24.15.0으로 검사했다. 설치 검증은 실제 설치·제거·바로가기

## 기존 성능 비교 방법: 금지 지시 이전 기록

Windows 11 Pro 10.0.26300, Ryzen 5 5600X, 논리 CPU 12개 환경이다.
원본과 수정본 모두 release `opt-level=s`, LTO, 동일한 웹 자산을 사용한다.
안전한 probe 복사본은 독립된 앱/단일 인스턴스 식별자와 가짜 설정을 사용하고
자동 적용·자동 시작·업데이트를 차단한다. 실제 설치본을 실행하지 않는다.
창은 오프스크린에서 NOACTIVATE로 표시하며 게임을 대상으로 삼지 않는다.

규칙 0개와 가짜 규칙 50개를 각각 측정한다. 상황은 백그라운드, 표시,
최소화, 숨김, 재표시, 닫기, 재생성, 다시 닫기 순서다. 약 0.5초 간격으로
본체 및 자식 WebView2의 작업 집합·private bytes·CPU·스레드·핸들을 수집하고,
각 상황의 처음 5초를 제외한 중앙값을 사용한다.
CPU는 **논리 CPU 한 개를 100%로 계산한 값**이다. 전체 시스템 기준은 12로 나눈다.
작업 집합 합계는 공유 페이지를 중복 계산할 수 있어 실제 물리 RAM 절감과 같지 않다.
private bytes는 사적 커밋 크기다. 짧은 표본의 0%는 영구적인 CPU 0을 뜻하지 않는다.

실행은 순차적으로 진행하며 게임·설치본은 비교 대상으로 사용하지 않았다.
외부 창 이벤트와 시스템 캐시는 완전히 고정하지 못했으므로 결과를 모든 PC의
보장된 절감량이나 실제 게임 실행 시 수치로 해석하면 안 된다.
상태 전송량은 JSON 응답 크기이며 전체 IPC 프로토콜의 헤더/이벤트 트래픽은 제외한다.
