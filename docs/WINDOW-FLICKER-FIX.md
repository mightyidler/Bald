# 창 프레임 깜빡임 수정 기록

2026-10-09. 버전 0.1.2 유지. 실제 게임을 실행하거나 조작하지 않았으며 릴리즈·push는 하지 않았다.

## 확인한 문제와 수정

- `Watcher::start → scan → enumerate_windows → ApplicationRule → WindowController::make_borderless`가 자동 적용 경로다. 표시·생성 이벤트와 기존 4초 점검을 사용한다. 창 식별은 PID, 실행 파일, 최상위 창, 소유 창 여부, 도구 창 여부와 등록 규칙을 사용한다. 가시성은 게임 렌더링 준비 완료를 의미하지 않는다.
- 일반 창의 `make_borderless_style`은 스타일 비트가 이미 제거됐으면 반환한다. 이번에는 STYLE 또는 EXSTYLE 한쪽만 바뀌는 경우 다른 쪽에 같은 값을 다시 쓰는 것도 생략했다. 실제 변경 뒤에만 프레임 재계산을 요청한다.
- 메이플스토리의 `clip_native_frame`은 논리적 캡션과 스타일을 유지하고 DWM 비클라이언트 그림을 끈 뒤 내용 영역으로 region을 제한한다. 기존 코드는 region만 달라져도 DWM 정책 설정과 별도 `SWP_FRAMECHANGED`를 함께 호출했다. 이제 관찰한 DWM 렌더링이 이미 꺼져 있으면 region만 복구한다. `SetWindowRgn` 자체에서 발생하는 필요한 프레임 계산까지 없애는 것은 아니다.
- 실제 Win32 모사 창에서 별도 프레임 요청을 다시 활성화하면 새 회귀 테스트가 실패했다. 수정한 상태에서는 영역 복구 중 프레임 변경 통지가 1회이며, 같은 상태의 다음 적용은 추가 통지 없이 반환한다. 이것은 중복 계산을 확인한 결과이며 실제 게임의 깜빡임 원인을 확정한 결과는 아니다.
- 기존 `ApplicationRule::matches`는 실행 파일 경로가 일치하면 창 클래스 힌트를 무시했다. 같은 프로세스의 스플래시/런처에 자동 적용할 수 있는 조건이다. `matches_automatic_window`를 추가해 자동 적용·드래그 대상에는 클래스도 확인한다. 수동 복원은 기존 프로세스 범위를 유지한다. 클래스 힌트가 없는 기존 등록은 기존 동작을 유지한다.

## 이벤트와 수명주기

- `watcher.rs`: 생성/폐기/표시/숨김, 최소화 시작/복원 시작, 이동 종료, 추적 창의 위치 변경을 큐에 넣는다. 기존 프레임/드래그 상태를 사용하며 별도의 복잡한 상태 머신은 추가하지 않았다.
- 콜백에서는 PID와 이벤트 시각을 수집하고 스캔을 예약한다. 파일 기록, 창 열거, DWM·좌표 조회는 스캐너에서 처리한다. 사용자 지정 드래그 중의 위치 이벤트는 스캔을 예약하지 않는다.
- 이벤트 큐는 최대 256개이며 초과 시 가장 오래된 항목을 버린다. 이벤트 폭주 시 모든 이벤트가 기록된다고 보장하지 않는다. 스캔 예약은 기존 방식으로 병합한다.
- 이벤트는 새 창을 직접 수정하거나 이전 HWND의 상태를 새 HWND에 복사하지 않는다. 매 스캔에서 현재 창을 다시 열거한다. `managed_windows`의 PID·소유 마커 검증으로 종료/재생성된 창의 스냅샷과 저장 region을 정리한다.
- 최소화/복원 이벤트는 점검을 예약할 뿐, 그 이유만으로 스타일·프레임을 다시 설정하지 않는다. Microsoft 문서에서 `EVENT_SYSTEM_MINIMIZEEND`는 복원이 완료된 시점이 아니라 복원 직전 이벤트다. 이후 표시/위치 이벤트 및 기존 점검에서도 현재 상태를 확인한다.

## 진단 로그

- `diagnostics.rs`의 공통 단조 시계로 콜백 수신 시각과 작업 시각을 마이크로초 단위로 비교한다. `%TEMP%/Bald-frame-state-<BALD PID>.jsonl`에 기록한다. 파일은 기존 방식대로 512 KiB에서 순환한다.
- 이벤트 기록은 디버그 빌드에서 기본 활성화된다. 릴리즈에서는 기존 `--window-diagnostics` 옵션으로 활성화할 수 있다. 기존 작업별 frame 기록은 유지한다.
- PID/HWND, 이벤트 번호·Windows 이벤트 tick, 수신 시각과 나중에 관찰한 스냅샷 시각, 생존/가시성/최소화/최대화, STYLE/EXSTYLE, 관심 프레임 비트, DWM 렌더링과 화면 좌표 경계, 외곽 사각형, 클라이언트 크기·화면 원점을 기록한다.
- 스타일 API 결과와 오류, 일반 적용 및 DWM 정책 프레임 요청의 플래그·결과, 정책 변경과 영역만 복구한 경우를 구분한다. HWND 선택/제외도 별도 단계로 기록한다. 반환값 0은 마지막 오류가 0인지 함께 검사한다.
- 이벤트 로그의 창 정보는 콜백 순간이 아니라 큐 처리 시점의 관찰이다. 실제 게임이 처음 표시되기 전의 모든 변화를 포착하는 로그는 아니다.
- 이번 모사 창 로그에서 `native_region_only_repair → native_region_applied` 동안 STYLE `14cf0000`, EXSTYLE `08000180`, DWM 렌더링 false, 내용 크기 776×536 및 화면 원점이 유지되는 것을 확인했다. 실제 메이플스토리 재현 로그는 수집하지 않았다.

## 보존한 동작과 채택하지 않은 조치

- 기존 region/DWM 복원, 저장 스타일, 클라이언트 위치 보정, 최소화 상태 보존, 메이플 드래그의 `SWP_NOSENDCHANGING` 처리는 유지한다.
- 짧은 주기의 스타일 덮어쓰기, 추가 고정 지연, 게임 숨김/재표시, 오버레이, 코드 주입은 추가하지 않았다. 초기 HWND 선택을 개선했지만 렌더링 준비를 임의 시간으로 추정하지 않는다.
- `DWMWA_BORDER_COLOR/DWMWA_COLOR_NONE` 실험은 이번 변경에 추가하지 않았다. Windows 11 build 22000부터 지원되며 DWM 테두리 선만 억제한다. 논리적 캡션과 흰 영역 문제를 해결한다는 근거가 없고 실제 게임 비교 검증도 없으므로 별도 실험 후보로 남긴다.

## 실행한 검증

- `cargo fmt --check`, `cargo check`, `cargo build`, `git diff --check`: 통과. 개발 실행 파일은 `target/debug/bald.exe`다. 자동 실행하지 않았다.
- 최종 `cargo test -- --test-threads=1`: 55 통과, 0 실패, 6 제외. 제외된 항목은 실제 게임/권한/아이콘 수동 검사와 별도 실행하는 작업자 테스트다.
- 새 영역 복구 테스트: 불필요한 프레임 요청을 임시로 복원했을 때 실패(exit 101), 수정 복구 후 통과. 스플래시 클래스 제외 테스트도 통과했다.
- 중간 전체 검사 한 번은 기존 복원/메이플 테스트 4개가 실패했다. 동일 최종 코드의 재검사에서는 모두 통과했다. 테스트가 실제 데스크톱의 마우스 버튼·DWM 상태를 사용하므로 간헐 실패 원인은 이번 작업에서 확정하지 않았다.
- 복원 반복, 사용자 region/원래 클래식 그림 보존, 해상도 변경, 최소화 상태 유지, 오래된 PID 거부, 메이플 Y축 드래그, 종료 시 복원 관련 모사 Win32 테스트가 최종 검사에 포함된다. JavaScript/TypeScript는 변경하지 않았다.

## 실제 게임에서 남은 확인

메이플 최소화·복원 30회, 제거→복원→제거와 지정 영역 드래그, 자동 적용 냉시작 10회, 다른 게임 2~3종, HWND 재생성·해상도 변경·다중 모니터/DPI 시험은 이번에 직접 수행하지 않았다. 최초 표시 이전 프레임 노출을 외부 프로그램에서 완전히 막는다고 보장하지 않는다.

흰 박스가 남으면 이벤트 수신·정책 변경·영역 복구 시각과 영상을 비교해야 한다. 스타일 변화 없는 프레임 그림, 초기 빈 렌더링 영역, 자식/보조 창을 구분하기 전에는 재적용 빈도를 높이거나 게임별 처리를 추가하지 않는다.
